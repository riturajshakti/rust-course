# 11.2 — Rc and Shared Ownership

## What You'll Learn

- `Rc<T>` for many owners of one value, and `Rc::strong_count`
- Why `Rc::clone(&a)` is the convention over `a.clone()`
- `Rc<T>` gives read-only access, and the `E0596` you get when you forget
- `Rc` is single-threaded: the `Send` error when you cross a thread boundary

## Coming From Another Language

| Other | Rust |
|---|---|
| JS/Python: GC, any number of references | `Rc<T>`, refcounted, freed at zero |
| Go: GC handles sharing | `Rc<T>` for single-threaded, `Arc<T>` for multi |
| C++ `std::shared_ptr<T>` | `Rc<T>` (non-atomic) / `Arc<T>` (atomic) |

Ownership says one owner. `Rc<T>` is the escape hatch: the value lives on the
heap with a reference count, every clone bumps the count, every drop decrements
it, and the value is freed at zero. The price is that the value is **immutable**
through the `Rc`.

## Rc::new and strong_count

```rust
use std::rc::Rc;

fn main() {
    let a = Rc::new(String::from("shared"));
    println!("count = {}", Rc::strong_count(&a));
    let b = Rc::clone(&a);
    println!("count = {}", Rc::strong_count(&a));
    {
        let c = Rc::clone(&a);
        println!("count = {}", Rc::strong_count(&a));
        println!("{} {} {}", a, b, c);
    }
    println!("count = {}", Rc::strong_count(&a));
    drop(b);
    println!("count = {}", Rc::strong_count(&a));
    println!("{} {}", a.len(), a.to_uppercase());
}
```

Output:

```
count = 1
count = 2
count = 3
shared shared shared
count = 2
count = 1
6 SHARED
```

`c` going out of scope at the closing brace drops the count back to 2 without
any explicit call. Methods on the inner `String` work straight through the `Rc`.

## Rc::clone vs .clone()

They do exactly the same thing. `Rc::clone(&a)` is the convention because it
reads as "cheap refcount bump," while `a.clone()` looks like a deep copy of the
payload.

```rust
let b = Rc::clone(&a);
let c = a.clone();
```

Use the associated-function form. Clippy will not complain either way, but every
Rust codebase you read uses `Rc::clone`.

## Drop runs once, at zero

```rust
use std::rc::Rc;

struct Noisy(&'static str);
impl Drop for Noisy {
    fn drop(&mut self) {
        println!("dropping {}", self.0);
    }
}

fn main() {
    let a = Rc::new(Noisy("payload"));
    let b = Rc::clone(&a);
    println!("count = {}", Rc::strong_count(&a));
    drop(a);
    println!("after first drop, count = {}", Rc::strong_count(&b));
    drop(b);
    println!("done");
}
```

Output:

```
count = 2
after first drop, count = 1
dropping payload
done
```

Dropping an `Rc` only drops the *handle*. `Noisy::drop` fires once, when the
last handle goes.

## Sharing a node between two owners

The canonical use: two structures that both need the same node.

```rust
use std::rc::Rc;

#[derive(Debug)]
struct Node {
    name: String,
    children: Vec<Rc<Node>>,
}

fn main() {
    let shared = Rc::new(Node { name: "lib".into(), children: vec![] });
    let a = Rc::new(Node { name: "app-a".into(), children: vec![Rc::clone(&shared)] });
    let b = Rc::new(Node { name: "app-b".into(), children: vec![Rc::clone(&shared)] });
    println!("{} {}", a.children[0].name, b.children[0].name);
    println!("shared count = {}", Rc::strong_count(&shared));
    println!("same node? {}", Rc::ptr_eq(&a.children[0], &b.children[0]));
    println!("a == b? {}", Rc::ptr_eq(&a, &b));
}
```

Output:

```
lib lib
shared count = 3
same node? true
a == b? false
```

Count is 3: the original plus one clone in each parent. `Rc::ptr_eq` compares
*addresses*, not contents — it answers "is this literally the same allocation?"
and never calls `PartialEq` on `T`.

## Rc gives immutable access only

```rust
use std::rc::Rc;

fn main() {
    let v = Rc::new(vec![1, 2, 3]);
    v.push(4);
}
```

Does not compile — intentional:

```
error[E0596]: cannot borrow data in an `Rc` as mutable
 --> src/main.rs:5:5
  |
5 |     v.push(4);
  |     ^ cannot borrow as mutable
  |
  = help: trait `DerefMut` is required to modify through a dereference, but it is not implemented for `Rc<Vec<i32>>`
```

Of course not — several owners holding `&mut` to the same value is exactly what
the borrow checker exists to prevent. Wrap the inner value in a `RefCell` to
get mutation back; that is lesson 11.3 and the `Rc<RefCell<T>>` pattern.

## Rc::get_mut

If the count is exactly 1, there is no aliasing, so mutation is safe. `get_mut`
returns `Option<&mut T>`.

```rust
use std::rc::Rc;

fn main() {
    let mut c = Rc::new(String::from("hi"));
    if let Some(s) = Rc::get_mut(&mut c) {
        s.push_str(" there");
    }
    println!("{}", c);

    let d = Rc::clone(&c);
    println!("{}", Rc::get_mut(&mut c).is_none());
    drop(d);
    println!("{}", Rc::get_mut(&mut c).is_some());
}
```

Output:

```
hi there
true
true
```

Related: `Rc::make_mut` clones the inner value when the count is above 1 and
hands back a `&mut` to the now-unique copy — copy-on-write for `Rc`.

## Rc::try_unwrap

Takes the value back out, but only if you hold the last handle.

```rust
use std::rc::Rc;

fn main() {
    let a = Rc::new(vec![1, 2, 3]);
    println!("{:?}", Rc::try_unwrap(a));

    let b = Rc::new(vec![4, 5]);
    let _b2 = Rc::clone(&b);
    match Rc::try_unwrap(b) {
        Ok(v) => println!("unwrapped {:?}", v),
        Err(rc) => println!("still shared, count = {}", Rc::strong_count(&rc)),
    }
}
```

Output:

```
Ok([1, 2, 3])
still shared, count = 2
```

The `Err` hands your `Rc` back, so nothing is lost. Unlike `Box`, you cannot
write `*rc` to move the value out — there may be other owners.

## Rc is single-threaded

`Rc<T>` is neither `Send` nor `Sync`, because the refcount is a plain
non-atomic integer. Trying to move one into a thread:

```rust
use std::rc::Rc;
use std::thread;

fn main() {
    let data = Rc::new(vec![1, 2, 3]);
    let d = Rc::clone(&data);
    thread::spawn(move || {
        println!("{:?}", d);
    })
    .join()
    .unwrap();
}
```

Does not compile — intentional:

```
error[E0277]: `Rc<Vec<i32>>` cannot be sent between threads safely
   --> src/main.rs:7:19
    |
  7 |       thread::spawn(move || {
    |       ------------- ^------
    |       |             |
    |  _____|_____________within this `{closure@src/main.rs:7:19: 7:26}`
    | |     |
    | |     required by a bound introduced by this call
  8 | |         println!("{:?}", d);
  9 | |     })
    | |_____^ `Rc<Vec<i32>>` cannot be sent between threads safely
    |
    = help: within `{closure@src/main.rs:7:19: 7:26}`, the trait `Send` is not implemented for `Rc<Vec<i32>>`
note: required by a bound in `spawn`
    |
128 |     F: Send + 'static,
    |        ^^^^ required by this bound in `spawn`
```

This is a feature: a racy refcount means double-free. Swap `Rc` for `Arc` and it
compiles — lesson 11.4.

## Rc of unsized types

`Rc<str>` and `Rc<[T]>` store the data inline with the count, so cloning is a
refcount bump instead of a string copy.

```rust
use std::rc::Rc;

fn main() {
    println!("{} {}", size_of::<Rc<i32>>(), size_of::<Rc<[i32]>>());
    let s: Rc<str> = Rc::from("slice");
    println!("{} {}", s, s.len());
}
```

Output:

```
8 16
slice 5
```

`Rc<str>` is a good fit for an interned string shared across many structs — one
pointer-sized clone, no reallocation.

## Quick Reference

| Call | Returns | Notes |
|---|---|---|
| `Rc::new(v)` | `Rc<T>` | count starts at 1 |
| `Rc::clone(&a)` | `Rc<T>` | bumps count; preferred form |
| `Rc::strong_count(&a)` | `usize` | live handles |
| `Rc::weak_count(&a)` | `usize` | see lesson 11.7 |
| `Rc::ptr_eq(&a, &b)` | `bool` | same allocation? |
| `Rc::get_mut(&mut a)` | `Option<&mut T>` | `Some` only if count == 1 |
| `Rc::make_mut(&mut a)` | `&mut T` | clones `T` if count > 1 |
| `Rc::try_unwrap(a)` | `Result<T, Rc<T>>` | `Ok` only if count == 1 |
| `Rc::downgrade(&a)` | `Weak<T>` | non-owning; lesson 11.7 |
| `Rc<T>` size | 8 bytes | 16 for `Rc<str>` / `Rc<[T]>` |
| thread safety | none | not `Send`, not `Sync` |

## Common Mistakes

**Writing `a.clone()` for an `Rc`.** Works, but hides that it's a refcount bump.
Write `Rc::clone(&a)`.

**Expecting to mutate through an `Rc`.** You get `E0596`. Use
`Rc<RefCell<T>>` (lesson 11.3) or `Rc::get_mut` when the count is 1.

**Reaching for `Arc` by default.** Atomic increments cost more. Use `Rc` unless
the value genuinely crosses threads.

**Assuming `Rc::ptr_eq` compares values.** It compares pointers. Two `Rc`s with
equal contents and different allocations return `false`.

**Building a cycle of `Rc`s.** The count never reaches zero and the memory
leaks. Lesson 11.7 shows it happening and the `Weak` fix.

## Exercises

1. Create one `Rc<String>`, clone it into a `Vec` of five handles, print
   `strong_count`, then `truncate` the vec to two and print the count again.
2. Build `struct Doc { text: Rc<str> }` and three `Doc`s sharing one text.
   Confirm with `Rc::ptr_eq` that all three point at the same allocation.
3. Write a function taking `Rc<Vec<i32>>` that returns `Ok(vec)` via
   `Rc::try_unwrap` or the sum of the elements if it is still shared. Call it
   both ways.
4. Use `Rc::make_mut` to append to an `Rc<Vec<i32>>` while a second handle is
   alive, then print both handles and explain the values you see.
5. Try sending an `Rc` into `thread::spawn`, capture the error, then make it
   compile with the smallest change you can.
