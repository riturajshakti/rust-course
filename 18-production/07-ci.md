# 18.7 — CI with GitHub Actions

## What You'll Learn

- A complete `ci.yml`: fmt, clippy, test, release build
- Caching `target/` with `Swatinem/rust-cache`, and why it matters so much here
- A Postgres service container plus `SQLX_OFFLINE` for SQLx integration tests
- `cargo-deny`, `cargo-llvm-cov`, a release job, and concurrency groups

> **On verification.** GitHub Actions cannot run in this environment, so every
> workflow below is presented as a file. There are **no captured run logs in
> this lesson** — nothing here is a fabricated transcript. The YAML is complete
> and ready to commit.

## Coming From Another Language

| Other | Rust |
|---|---|
| `npm ci` (~30 s, prebuilt) | `cargo build` compiles every dependency from source |
| cache `node_modules` | cache `~/.cargo` **and** `target/` — the second is the point |
| lint is advisory | `clippy -D warnings` is a hard gate, and worth it |
| no compile step to cache | an uncached Rust CI job can take 10+ minutes |

Caching is the difference between a 90-second pipeline and an eight-minute one.
Everything else is conventional.

## The shape of a Rust pipeline

Five jobs, which the rest of this lesson builds one at a time and assembles at
the end:

| Job | Runs | Needs a database |
|---|---|---|
| `check` | `cargo fmt --check`, `cargo clippy -D warnings` | no |
| `test` | `cargo test`, matrix over toolchains | no |
| `integration` | migrations + tests against Postgres | **yes** |
| `audit` | `cargo-deny`: advisories, licenses, bans | no |
| `build` | `cargo build --release --locked` | no |

Three environment variables belong at the workflow level:

```yaml
env:
  CARGO_TERM_COLOR: always
  RUSTFLAGS: "-D warnings"
  CARGO_INCREMENTAL: 0
```

`CARGO_INCREMENTAL: 0` — incremental metadata is large, invalidates on every
commit, and makes the cache worse than useless. `RUSTFLAGS: "-D warnings"` fails
the build on any warning. `CARGO_TERM_COLOR` makes the log readable.

`--locked` on every cargo command fails if `Cargo.lock` would need updating, so
CI builds exactly what you committed.

## dtolnay/rust-toolchain

```yaml
- uses: dtolnay/rust-toolchain@stable
  with:
    components: rustfmt, clippy
    targets: x86_64-unknown-linux-musl
```

It is the standard choice: fast, no caching of its own (that is
`rust-cache`'s job), and the version is in the `uses:` ref.

| Ref | Meaning |
|---|---|
| `@stable` | current stable |
| `@beta`, `@nightly` | those channels |
| `@1.99.1` | an exact version |
| `@master` with `toolchain:` | version from an input or expression |

If you committed a `rust-toolchain.toml` (18.5), use `@master` so the file wins:

```yaml
- uses: dtolnay/rust-toolchain@master
  with:
    toolchain: ${{ steps.toolchain.outputs.channel }}
```

Simpler: keep `@stable` and let `rust-toolchain.toml` override it on first cargo
invocation — rustup honours the file automatically.

## Caching, and why target/ dominates

```yaml
- uses: Swatinem/rust-cache@v2
  with: { shared-key: "ci", cache-on-failure: true }
```

`Swatinem/rust-cache` caches `~/.cargo/registry`, `~/.cargo/git` and `target/`,
and — the part a hand-rolled `actions/cache` gets wrong — it **prunes** first: it
drops incremental artifacts, your own crate's stale outputs and
no-longer-referenced dependencies, so the cache does not grow without bound and
blow the 10 GB repository limit.

Why `target/` matters more than the registry: `~/.cargo/registry` holds
downloaded `.crate` source files, maybe 100 MB and a few seconds of network.
`target/` holds the *compiled* artifacts of 300 dependency crates — hundreds of
CPU-seconds. Node's cache saves a download; Rust's saves a compile.

| Key input | Effect on the cache key |
|---|---|
| `Cargo.lock` | changes invalidate dependency artifacts |
| `rustc` version | a new stable release invalidates everything |
| job name + `shared-key` | separates or shares caches between jobs |
| `~/.cargo/config.toml`, `RUSTFLAGS` | different flags, different cache |

Two rules that follow. Jobs with different `RUSTFLAGS` or features get separate
caches, so a job that builds with `--all-features` will not warm one that does
not. And GitHub caches are **immutable per key and branch-scoped**: a PR reads
`main`'s cache but writes its own, so the first run on a new branch is partially
cold no matter what. Keep `main` green and its cache fresh.

`cache-on-failure: true` saves the cache even when tests fail, so a flaky test
does not cost you the next run's compile too.

## Clippy as a gate

```yaml
- run: cargo clippy --all-targets --all-features -- -D warnings
```

`--all-targets` includes tests, benches and examples — without it, lint
failures in test code reach `main`. `-D warnings` turns every lint into an
error.

Allow specific lints in code rather than loosening the flag:

```rust
#[allow(clippy::too_many_arguments)]
fn build_query(/* ... */) { }
```

Or project-wide in `Cargo.toml`:

```toml
[lints.clippy]
too_many_arguments = "allow"
unwrap_used = "warn"
expect_used = "warn"
```

`[lints]` in `Cargo.toml` is better than `#![deny(...)]` in `lib.rs`: it applies
to the whole package including tests, and it is visible where dependencies are.

## A matrix over stable and beta

```yaml
  test:
    name: test / ${{ matrix.rust }}
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix: { rust: [stable, beta] }
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@master
        with: { toolchain: "${{ matrix.rust }}" }
      - uses: Swatinem/rust-cache@v2
        with: { key: "${{ matrix.rust }}" }
      - run: cargo test --all-features --workspace
```

`fail-fast: false` so a `beta` failure does not cancel the `stable` run you
actually care about. `key: ${{ matrix.rust }}` gives each toolchain its own
cache — they cannot share artifacts.

Beta catches regressions about six weeks before they hit your users. Make it
non-blocking in required checks (below) so an upstream bug does not stop your
merges.

Add an MSRV job if you publish a library:

```yaml
      - uses: dtolnay/rust-toolchain@master
        with:
          toolchain: "1.90.0"
      - run: cargo build --locked
```

Build, don't test, for MSRV: dev-dependencies often need a newer compiler than
your crate does.

## A Postgres service container

This is the job that matters for the Module 17 stack.

```yaml
  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17-alpine
        env:
          POSTGRES_USER: postgres
          POSTGRES_PASSWORD: postgres
          POSTGRES_DB: app_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s --health-timeout 5s --health-retries 10
    env:
      DATABASE_URL: postgres://postgres:postgres@localhost:5432/app_test
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
      - name: Install sqlx-cli
        run: cargo install sqlx-cli --no-default-features --features rustls,postgres --locked
      - run: sqlx migrate run
      - run: cargo test --all-features --workspace
```

The `options:` health check is not optional. Without it, the runner starts the
job as soon as the container *starts*, and your first connection races Postgres'
initialisation — a flake that reproduces maybe one run in five.

The host is `localhost` because the port is mapped to the runner. (In a
container-based job it would be the service name, `postgres`.)

`cargo install sqlx-cli` recompiles on every run and costs a minute or two.
Faster:

```yaml
      - uses: taiki-e/install-action@v2
        with: { tool: sqlx-cli }
```

`taiki-e/install-action` downloads a prebuilt binary — seconds instead of
minutes — and works for `cargo-nextest`, `cargo-llvm-cov`, `cargo-deny` and
others.

## SQLX_OFFLINE and sqlx prepare

`sqlx::query!` validates SQL **at compile time** by connecting to a live
database. That means `cargo build` normally needs `DATABASE_URL` — painful in CI
and impossible in a Docker build (18.6).

The fix is to commit the query metadata:

```bash
cargo sqlx prepare --workspace
git add .sqlx
git commit -m "update sqlx query metadata"
```

That writes `.sqlx/query-*.json`, one file per macro invocation. Then:

```yaml
    env:
      SQLX_OFFLINE: "true"
```

With `SQLX_OFFLINE=true` the macros read `.sqlx/` instead of connecting. Your
`check` and `build` jobs then need no database at all — only the integration job
does, and it needs one for the *queries at runtime*, not for compilation.

Guard against stale metadata, which is the failure this introduces:

```yaml
      - name: Verify .sqlx is current
        env:
          SQLX_OFFLINE: "false"
        run: cargo sqlx prepare --workspace --check
```

`--check` fails if a query changed without `.sqlx/` being regenerated. Run it in
the integration job where the database exists. Without this step someone edits a
query, forgets to re-prepare, CI passes offline against old metadata, and
production gets a column mismatch.

Set `SQLX_OFFLINE: "true"` at the workflow level and override to `"false"` only
in that one step.

## Security auditing

```yaml
  audit:
    name: cargo-deny
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: EmbarkStudios/cargo-deny-action@v2
        with: { command: "check advisories bans licenses sources" }
```

It reads `deny.toml` from the repository root; lesson 18.9 has a complete one,
with `advisories`, `bans`, `licenses` and `sources` sections.

`cargo-deny` supersedes `cargo-audit`: same advisory database, plus license
policy, duplicate-version detection and source restrictions. If you only want
vulnerabilities, `cargo-audit` is the smaller tool:

```yaml
      - uses: rustsec/audit-check@v2
        with: { token: "${{ secrets.GITHUB_TOKEN }}" }
```

Run the audit on a schedule too — a new advisory against an unchanged dependency
is exactly what you want to hear about:

```yaml
on:
  schedule:
    - cron: "0 6 * * 1"
```

`licenses` is the clause that catches real problems: a transitive GPL dependency
in a proprietary service is a legal issue nobody notices until shipping.

## Coverage with cargo-llvm-cov

Same `services:` and `env:` blocks as the integration job above, with these
steps:

```yaml
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          components: llvm-tools-preview
      - uses: Swatinem/rust-cache@v2
      - uses: taiki-e/install-action@v2
        with: { tool: "cargo-llvm-cov,sqlx-cli" }
      - run: sqlx migrate run
      - name: Collect coverage
        run: cargo llvm-cov --all-features --workspace --lcov --output-path lcov.info
      - uses: codecov/codecov-action@v5
        with: { files: lcov.info, token: "${{ secrets.CODECOV_TOKEN }}" }
```

`llvm-tools-preview` is required (despite the name it is stable). `cargo-llvm-cov`
uses LLVM source-based coverage — accurate, unlike the older `tarpaulin`
approach.

For a readable local summary:

```bash
cargo llvm-cov --all-features --workspace
cargo llvm-cov --html --open
```

Note coverage needs its own build flags, so it will not reuse the `test` job's
cache. It roughly doubles compile time; many teams run it only on `main` or
nightly rather than every PR.

## A release job

```yaml
name: Release

on:
  push:
    tags: ["v*"]

jobs:
  artifacts:
    name: ${{ matrix.target }}
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        include:
          - { target: x86_64-unknown-linux-gnu,  os: ubuntu-latest }
          - { target: x86_64-unknown-linux-musl, os: ubuntu-latest }
          - { target: aarch64-apple-darwin,      os: macos-latest }
    env:
      SQLX_OFFLINE: "true"
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with: { targets: "${{ matrix.target }}" }
      - uses: Swatinem/rust-cache@v2
        with: { key: "${{ matrix.target }}" }
      - name: Install musl tools
        if: endsWith(matrix.target, '-musl')
        run: sudo apt-get update && sudo apt-get install -y musl-tools
      - run: cargo build --release --locked --target ${{ matrix.target }}
      - name: Package
        run: |
          tar -czf myapi-${{ matrix.target }}.tar.gz \
            -C target/${{ matrix.target }}/release myapi
      - uses: actions/upload-artifact@v4
        with:
          name: myapi-${{ matrix.target }}
          path: myapi-${{ matrix.target }}.tar.gz

  publish:
    needs: artifacts
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/download-artifact@v4
        with: { merge-multiple: true }
      - uses: softprops/action-gh-release@v2
        with: { files: "*.tar.gz", generate_release_notes: true }
```

Each target builds on a native runner — no QEMU, no cross-compilation
toolchain. `SQLX_OFFLINE: "true"` is what makes this work with no database in
the release pipeline. `permissions: contents: write` is required for the release
upload; scope it to the one job that needs it.

## Concurrency groups

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}
```

Push three times to a PR and without this you get three full pipelines, two of
which are already obsolete. The group keys on workflow plus ref, so a new push
to the same branch cancels the previous run.

The conditional matters: `main` runs are **not** cancelled. Those produce your
cache and your deployment, and cancelling one mid-flight leaves a partially
warmed cache or a half-finished release.

For a deployment workflow you want the opposite — queue rather than cancel:

```yaml
concurrency:
  group: production-deploy
  cancel-in-progress: false
```

## Required status checks

With a matrix, the check names include matrix values (`test / stable`), which
makes branch-protection rules fragile. Add one aggregating job:

```yaml
  ci-success:
    name: CI
    if: always()
    needs: [check, test, integration, audit]
    runs-on: ubuntu-latest
    steps:
      - name: Fail if any dependency failed
        if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')
        run: exit 1
      - run: echo "all required checks passed"
```

Then require only `CI` in branch protection. Adding or renaming a job never
needs a settings change, and `beta` can stay out of `needs` so it reports
without blocking.

`if: always()` is essential — without it the job is skipped when a dependency
fails, and a skipped required check reads as "pending" forever.

## Speeding the pipeline up

In rough order of impact: `Swatinem/rust-cache@v2` (the one that matters —
`target/` is the prize), `CARGO_INCREMENTAL: 0`, `taiki-e/install-action` for
prebuilt tool binaries, `cargo nextest run` for parallel tests, splitting
fmt/clippy from test for fast feedback, `--locked` everywhere, and sharing a
`shared-key` across jobs that use identical flags.

One worth stating explicitly: do **not** run a separate `cargo check` job.
`cargo clippy` performs the same analysis plus lints, so running both compiles
your crate twice.

## The assembled workflow

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

env:
  CARGO_TERM_COLOR: always
  CARGO_INCREMENTAL: 0
  RUSTFLAGS: "-D warnings"
  SQLX_OFFLINE: "true"

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with: { components: "rustfmt, clippy" }
      - uses: Swatinem/rust-cache@v2
      - run: cargo fmt --all --check
      - run: cargo clippy --all-targets --all-features -- -D warnings

  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix: { rust: [stable, beta] }
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@master
        with: { toolchain: "${{ matrix.rust }}" }
      - uses: Swatinem/rust-cache@v2
        with: { key: "${{ matrix.rust }}" }
      - run: cargo test --all-features --workspace

  integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17-alpine
        env:
          POSTGRES_USER: postgres
          POSTGRES_PASSWORD: postgres
          POSTGRES_DB: app_test
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s --health-timeout 5s --health-retries 10
    env:
      DATABASE_URL: postgres://postgres:postgres@localhost:5432/app_test
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
      - uses: taiki-e/install-action@v2
        with: { tool: "sqlx-cli,cargo-nextest" }
      - run: sqlx migrate run
      - name: Verify .sqlx is current
        env: { SQLX_OFFLINE: "false" }
        run: cargo sqlx prepare --workspace --check
      - run: cargo nextest run --all-features --workspace

  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: EmbarkStudios/cargo-deny-action@v2
        with: { command: "check advisories bans licenses sources" }

  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
      - run: cargo build --release --locked

  ci-success:
    name: CI
    if: always()
    needs: [check, test, integration, audit, build]
    runs-on: ubuntu-latest
    steps:
      - if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled')
        run: exit 1
      - run: echo "all required checks passed"
```

## Quick Reference

| Need | Step |
|---|---|
| Toolchain | `dtolnay/rust-toolchain@stable` |
| Cache | `Swatinem/rust-cache@v2` |
| Prebuilt cargo tools | `taiki-e/install-action@v2` with `tool:` |
| Format gate | `cargo fmt --all --check` |
| Lint gate | `cargo clippy --all-targets --all-features -- -D warnings` |
| Tests | `cargo test --all-features --workspace` |
| Faster tests | `cargo nextest run` |
| Reproducible deps | `--locked` |
| No DB needed to compile | `SQLX_OFFLINE: "true"` + committed `.sqlx/` |
| Regenerate metadata | `cargo sqlx prepare --workspace` |
| Catch stale metadata | `cargo sqlx prepare --workspace --check` |
| Service readiness | `options: --health-cmd "pg_isready -U postgres"` |
| Advisories + licenses | `EmbarkStudios/cargo-deny-action@v2` |
| Coverage | `cargo llvm-cov --lcov --output-path lcov.info` |
| Cancel stale runs | `concurrency.group` + `cancel-in-progress` |
| One required check | aggregating job with `if: always()` |

## Common Mistakes

**No `target/` cache.** The job recompiles 300 crates every run. This is the
difference between a 90-second and an 8-minute pipeline.

**Leaving `CARGO_INCREMENTAL` on.** Incremental artifacts bloat the cache and
invalidate on every commit, making it net-negative.

**A service container with no health check.** Tests race Postgres'
initialisation and flake about one run in five.

**Committing `.sqlx/` once and forgetting it.** CI passes offline against stale
metadata while production gets a column mismatch. Run `prepare --check`.

**`clippy` without `--all-targets`.** Lint failures in test code sail through.

**Requiring matrix job names in branch protection.** Rename a job or add a
toolchain and merges block on a check that no longer exists. Aggregate.

**`cancel-in-progress: true` on `main`.** You cancel the run that produces your
cache and your release.

## Exercises

1. Write the minimal three-job workflow (fmt/clippy, test, build) with
   `rust-cache`. Push twice and compare the two runs' durations.
2. Add a `beta` matrix entry with `fail-fast: false` and a per-toolchain cache
   key. Confirm each gets its own cache entry in the Actions UI.
3. Add a Postgres service with a health check and run one integration test
   against it. Remove the health check and see whether it flakes.
4. Commit `.sqlx/` via `cargo sqlx prepare`, set `SQLX_OFFLINE`, and confirm the
   `build` job needs no database. Then change a query without re-preparing and
   watch `prepare --check` catch it.
5. Add the aggregating `ci-success` job and make it the only required check.
   Rename `test` and confirm branch protection still works.
